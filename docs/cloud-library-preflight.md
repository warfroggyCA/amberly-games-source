# Cloud Library preflight

Run this in every fresh saved cloud session before planning image-dependent
implementation or promising review-artifact delivery. A saved configuration or
successful metadata lookup is not evidence that this executor can transfer files.

1. Read the task's private reference list and current Library skill. Preserve each
   exact Library identity/current version; keep private reference IDs out of public
   source. Read workspace and checkout instructions, activate the retained tools,
   and verify the installed Node and Next versions against the project's pins.
2. Verify the existing approved network settings in the supported environment UI
   when available. For this workflow the approved exact hosts include
   `chatgpt.com`, `oaisdmntpreastus.blob.core.windows.net`, and
   `oaisdmntprwestus.blob.core.windows.net`, and
   `oaisdmntprwestus3.blob.core.windows.net`, alongside the existing project hosts.
   Do not infer an active allowlist from a saved version number. Record whether
   the active configuration was actually visible. Inspect the returned hostname
   for every required reference, not just one sample: assets may use different
   regions. Preserve privacy and existing
   settings; request only observed missing hosts through the supported workflow.
3. Fetch the current bundled helpers into a private directory. For list/search
   results, pass the complete unchanged structured result, explicit selection and
   relative destination to the download helper. For other resolved references,
   use `prepare_materialize` and the current materialization guidance. Keep the
   destination on the executor that will consume the images. Never guess storage
   URLs, use a generic downloader for Library IDs, forward credentials manually,
   or switch executors to bypass restrictions.
4. Check each returned local path exists and has readable bytes. View the actual
   pixels on this executor and record which reference/version was inspected.
   Extracted text, image pointers and metadata are not pixel verification. Follow
   the task's bounded retry allowance; report failures instead of looping.
5. Generate a small synthetic output screenshot locally, inspect it, then save it
   through the current supported Library upload route. For batches with prepared
   tools, use the complete prepared-upload helper flow. Inspect every result and
   retain confirmed Library IDs and local identity metadata. No confirmed ID means
   no promised Library delivery. Do not switch routes after an uncertain write.
6. Record the fresh-session date, code head, configuration evidence, input byte and
   pixel result, output result and remaining blocker in the private project record.
   Restart services and perform the specified loopback/browser readiness checks.
   Continue independently authorized work while image-dependent work is blocked.

## Diagnosing a failure without exposing secrets

Separate metadata/authorization, materialization preparation, executor download,
pixel decoding, upload-tool discovery, byte upload and finalization. Report the
failed stage and sanitized hostname/status/error only. Never log signed query
strings, request headers, credentials or private image payloads. A credential-free
hostname probe can establish DNS or proxy behavior; it does not diagnose an
authenticated Library operation or prove a configuration rollout completed.

recovery. This check catches known transfer gaps; it cannot prevent every failure.
