# Superadmin access and usage

Release status is recorded by the annotated `amberly-games-2026-09-27-access-usage` tag. Until that tag exists, this document describes the release candidate; the tag records the deployed commit, protected verification, migration, backup rehearsal and live checks.

Open the Amberly menu, then **Administration → Access & Usage**. The entry and report are mounted only for superadmins, including in the Scrabble account menu. The report opens in a dialog rather than a separately addressable page. Members with invitation or history-export permissions do not gain report access. JSON and CSV reads independently verify the authenticated account and current active superadmin membership for the configured family; browser requests cannot choose a different family or actor.

## What the report means

- **Visits:** observed signed-in account activity, grouped until 30 minutes pass without a receipt. Overlapping tabs/devices share an account visit. A visit spanning multiple areas has a separate timeline row for each area; the total counts distinct visits. For a partial date range, the timeline shows only the observed portion within that range.
- **Estimated active time:** visible app use with interaction in the preceding 60 seconds, sampled every five seconds and sent about every 15 seconds. Hidden pages, offline periods and timer gaps over ten seconds are excluded. The initial visit receipt records zero active time. Server serialization caps total credited time per account to the elapsed time since its previous receipt, preventing overlapping tabs/devices from double-counting. Area changes discard pending time rather than crediting it to the wrong screen. This is an estimate, not physical board-game duration or proof of attention.
- **Screen views:** first observed area in a visit and changes between Games, Scrabble, Crokinole, Gym, History, Players, Settings and Administration. This does not capture every click, keystroke, internal scorer panel or game identifier. Local-only settings changes are not audited.
- **Saved actions:** existing Scrabble journals (without double-counting their audit envelopes), administrative audit records (including Crokinole actions), and saved Gym action metadata. The actor is the account making the change, not necessarily the player whose score changed. Names/email are current membership/profile labels. Historical actions have no inferred visit duration. Timestamps are server receipts, including delayed Gym uploads; Gym browser events are reports of interaction, not independently verified proof of attention.

Anonymous viewing-link visitors and unauthenticated/local previews are not tracked. Gym telemetry follows the authenticated profile-history identity and therefore requires the existing Gym history feature to be enabled. No IP addresses, user agents, raw URLs, viewing tokens, typed input, private notes or practice payloads are collected for this feature. Abandoned requests, abrupt page closure, network failure and service downtime can leave gaps; there is no online-now indicator or invented logout time.

The default window is seven local calendar days. The UI supports about a month at a time (30 calendar days safely across DST); the API limits the exact interval to 31 days. UTC instants are stored/exported; the UI shows the browser's time zone. Account, area and date filters apply to the totals; activity type filters the timeline only. Pagination preserves database timestamp precision. CSV exports the complete filtered timeline, not merely the loaded page, and rejects more than 10,000 rows with an instruction to narrow the filter. Spreadsheet formula prefixes are neutralized.

## Storage and release

Migration `20260927005922_access_usage.sql` adds append-only `scrabble.usage_pulses`, indexes, RLS and the restricted `scrabble.usage_gym_actions` projection. Existing game and Gym rows are unchanged. Gym's owner-only raw-record policies remain intact: the new function exposes only action name, receipt timestamp, actor and session reference, checks current family/superadmin membership, fixes its search path and grants execution only to `scrabble_runtime`. Browser roles receive no table or function grants.

There is no deletion/retention scheduler in this change. Retained activity is available in bounded date windows; automated pruning requires a separate retention decision. Runtime cannot update, delete or truncate receipts. Receipt UUIDs make retries idempotent. The server accepts at most one new receipt per second per account and bounds each receipt to 15 seconds. Browser tracking does not queue offline work or block gameplay; authorization/service-unavailable responses stop tracking until remount, so tracking coverage must not be presented as complete.

Before release, inspect hosted migration history, follow `docs/releasing.md` backup/restore approval requirements, apply only the reviewed missing migration, then deploy the matching app. With the migration absent, reports return a clear 503 and tracking fails quietly without breaking gameplay. On app rollback retain the additive table/function/indexes and all receipts. Verify real admin/member report access, an active session, background/idle exclusion and CSV download after rollout. Local mocked-browser tests are UI proof, not hosted end-to-end proof.
